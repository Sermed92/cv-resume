How I work

I decide what to isolate based on its impact on operations

Before splitting out a feature, I ask what happens if it becomes unavailable. If operations depend on it, I consider where it can run with the availability it needs and which dependencies it would still rely on.

I also look at what happens while it runs. If a task can wait and competes with critical workflows for resources, I prefer to isolate it so it can run without competing for resources with critical workflows.

When something is slow, the first step is to find the bottleneck

When an endpoint is slow, I start with observability tools to find out whether the delay is in the network, the service, or the database. If I need more data, I add instrumentation before deciding what to optimize.

If the database is the bottleneck, I check the query plan and indexes before considering a materialized view or caching. If the bottleneck is in the code, I optimize the part responsible for the delay.

I explain technical decisions

When I work with teams across disciplines, I explain what problem a technical decision solves and what it changes for the product in terms we can all discuss.
